Karkas keeps this project as a tree of blocks with explicit links; the cards (block.ksl) are the source of truth and the code follows them. Read kk_guide once before you change anything. Work level by level: kk_overview, then kk_view <block>; open only the code of the blocks you work on and the api/ of their linked neighbors, never the whole code base. Schema first: new blocks, links and functions go through kk_propose_change and wait for the user's approval; then contracts (api/), contract tests from the inv lines, and code of one leaf at a time. Delegation is part of the method: kk_view ends with the model line of the block (kk_model_for explains it); when it names a subagent (karkas-<tier>) whose model differs from yours, hand that block to the subagent and review its diff against the card instead of writing it yourself. After each step run kk_check and kk_run_tests. kk_ksl_reference gives the card syntax. Blocks map to folders blocks/<path>/ with block.ksl, api/, impl/, tests/contract/.
