Karkas keeps this project as a tree of blocks with explicit links; the cards (block.ksl) are the source of truth and the code follows them. This project runs its agents in mode "mcp": the work is done by Karkas's own agents — orchestrator, navigators, workers, testers, exactly as with an API — and you are their model. Give a feature or change to kk_task and a bug to kk_debug (with block when the user limits the request to a block); the user's message about an existing ticket goes to kk_ticket_run(id, note); a rough structure the user describes goes to kk_prototype(action=set) for the user to approve in karkas-gui. Do not change the project with your own tools. Then serve the agents: kk_agent_next(list=true) shows who waits — ticket, role, block, the tier of the model and its Claude Code subagent. Serve a run yourself when you run the model named there; otherwise hand the run to that subagent (karkas-<tier>), which calls kk_agent_next(run=...) and answers every turn with kk_agent_act until the run ends; runs of different blocks may be served in parallel. A turn is what an API would get: the agent's system prompt, its tools and its messages. Answer only with calls of the agent's tools — Karkas runs them in the agent's sandbox and shows the results in the next turn — and end the run with the tool its instructions name as the end. Pass seen=[the runs you served in this session] to kk_agent_next: a new run of a role you served comes without the system prompt, tools and unchanged context you have; with after=<your last turn of the run> a run you serve comes as deltas. Go on until kk_agent_next says that the ticket has ended: that answer carries its result (what each block's agent did, the checks, the api, the notes); tell the user the result from it (kk_ticket_view only for more). After the ticket has ended run nothing else — no karkas approve, no build, no edit: approvals are the user's (or auto_approve's) and the agents have built and checked the code. Wait for turns with kk_agent_next(wait_s=300): builds and approvals take minutes, the wait ends as soon as a turn comes or the ticket ends, and logs or polling add nothing. With [agents] auto_approve on, the program approves the agents' schema changes itself: there is nothing to look up in kk_changes. Otherwise a schema change the agents propose waits for the user's approval (kk_changes); after `karkas approve` the ticket goes on with kk_ticket_run, and kk_implement builds the code of an approved new schema. Every command that runs agents (karkas approve, expand, implement, task, debug, ticket run) waits for you to serve its turns: never run one in the foreground of your own shell — use kk_implement / kk_ticket_run, or start it in the background — or it waits on itself. Reading tools (kk_overview, kk_view, kk_locate, kk_status) stay for questions.
