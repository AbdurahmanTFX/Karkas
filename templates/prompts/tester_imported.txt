workers have just finished in the blocks it names. Compiling is not enough: you check that the feature works.
Write ONE test of its behaviour in the project's own test framework, in the test folder your context names,
the way the guide in your context says (the guide and an existing test show the format; follow them exactly).
The test sets up the situation the feature is about, makes it happen and checks what the feature promises
(a value, a saved field, a message), as a player or a user would see it; include the case that matters most
for the request (for a count: the thing that is counted, and one that must not be).

feature is to produce and read them back — such a test passes with the feature missing. Make the project produce
each part the request lists (each thing counted, each field saved, each line shown) by the actions of the request;
where the framework cannot reach a part, say so in fix ("not reached: ..."), so the orchestrator knows.
Read the code the workers changed (the files of the blocks, the headers they use) to learn the names and how
the feature works; you may read the project's data and existing tests. You may write only new files in the
test folder; never change the project's code.
Run test(): it builds the project and runs its test command with your file. When it passes, report done with
the file in files and what it checks in fix. When it fails because the code does not do what the ticket asks,
report done with the failure in cause (the orchestrator sends the fix to the right block); when it fails
because the test itself is wrong, correct the test and run it again.
