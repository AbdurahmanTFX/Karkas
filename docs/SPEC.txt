==========================================================================
1. СУТЬ ИДЕИ
==========================================================================

1.1 Проблема
  ИИ-агенты для программирования (Claude Code, Cursor, Copilot и др.) при
  каждой задаче заново изучают проект: ищут файлы, читают код,
  восстанавливают связи и только потом режут задачу на части. Цена
  запроса растёт вместе с размером проекта. Почти всю работу выполняет
  одна дорогая модель, её контекст засоряется, а знание о проекте между
  сессиями теряется. Человек, особенно не программист, получает «чёрный
  ящик»: проект растёт, ломается, и непонятно где.

1.2 Решение одним абзацем
  Проект с самого начала проектируется и хранится как иерархическая
  схема: дерево блоков (блок → подблоки → … → листья), между которыми
  проведены типизированные связи. Каждый блок — папка на диске с
  карточкой на компактном языке KSL, интерфейсом (настоящий заголовок
  C++), кодом и тестами. Сильная модель (оркестратор) видит только схему
  и никогда не видит код. Дешёвые модели работают каждая внутри своего
  блока, в своём изолированном контексте. Общаются они короткими
  структурированными тикетами, которые при спуске по иерархии не
  переписываются, а дополняются. Программа без ИИ, обычными
  алгоритмами, собирает схему, проверяет её соответствие коду и рисует
  картинку для человека.

1.3 Принципы
  П1  Схема — постоянная карта. На части делится не задача, а сам проект,
      один раз и надолго. Любая новая задача ложится на готовую карту.
  П2  Разделение знаний. Оркестратор знает идею и схему, но не код.
      Исполнитель знает код своего блока, но не идею и не чужой код.
  П3  Изолированные контексты. Агенты обмениваются только сообщениями
      фиксированной формы, а не свободной перепиской.
  П4  Цена запроса зависит от глубины пути к нужному блоку, а не от
      размера проекта.
  П5  Связь — это контракт. Каждая связь превращается в проверяемый
      интерфейс в коде и в тесты. Расхождение схемы и кода находит
      программа, а не ИИ.
  П6  Тикет дополняется, а не переписывается. Исходные факты неизменны.
  П7  Детерминизм везде, где возможно: раскладка картинки, сводки
      статусов, запуск тестов, проверка расхождений, история — без
      токенов.
  П8  Дешёвая модель по умолчанию, эскалация при неудаче.
  П9  Человек утверждает структуру (схему и интерфейсы), автоматика
      проверяет код (тесты).
  П10 Постоянны не агенты, а знание: карточки, интерфейсы, тесты, история
      ошибок. Агент для блока запускается в любой момент и сразу
      получает всё нужное о своём участке.
  П11 Karkas — прежде всего среда для ИИ. Форматы оптимизированы под
      модель (компактный английский текст), а картинка для человека
      строится из тех же данных без затрат токенов.

1.4 Отличие от существующих решений
  - Связка «оркестратор + подагенты» (подагенты Claude Code, LangGraph,
    CrewAI, Google ADK и др.) делит на части ЗАДАЧУ. Подагенты выполняют
    её и исчезают, постоянной карты проекта нет, следующая задача снова
    начинается с исследования.
  - Графы кода для агентов (codebase-memory-mcp, «карта репозитория» в
    Aider и аналоги) строят граф по синтаксису: вызовы, импорты,
    символы. В них нет смыслового слоя: назначения блоков, потоков
    исполнения, гарантий, типов связей, истории ошибок.
  - Karkas соединяет: постоянную иерархическую схему как источник
    правды, смысловой слой, отладку спуском по схеме дополняемыми
    тикетами, раздачу работы моделям разной цены и общую картинку для
    человека из той же схемы.
  - Готовые кирпичики (tree-sitter, SQLite, MCP, Graphviz, Claude API)
    используются как детали, а не изобретаются заново.

1.5 Ожидаемый эффект (гипотезы, проверяются замерами из раздела 17)
  - Оркестратор тратит сотни или единицы тысяч токенов на задачу,
    потому что читает вид схемы, а не код.
  - Код читают дешёвые модели и только внутри одного блока.
  - Стабильные части запросов (инструкции, справка KSL, интерфейсы)
    кэшируются.
  - Детерминированные части стоят ноль токенов.
  - Честное ограничение: на маленьких проектах накладные расходы на
    схему могут перевесить выгоду. Выигрыш ожидается на росте проекта,
    на доработках и на отладке.

1.6 Не входит в первую версию (v1)
  - Импорт существующих проектов (автоматическая нарезка готового кода
    на блоки) — этап 11.
  - Целевые проекты не на C++ — этап 11 (архитектура ДОЛЖНА это
    допускать: анализ кода и сборка — через адаптеры).
  - Демон/сервер, веб-интерфейс, совместная работа нескольких людей.
  - Обучение собственных моделей.

2. СЛОВАРЬ ТЕРМИНОВ
==========================================================================

  Целевой проект  Проект, который разрабатывается с помощью Karkas
                  (например, аудиоконвейер wavkit). Не путать с самой
                  программой Karkas.
  Схема           Дерево блоков + граф связей + карточки.
  Блок            Единица схемы с одной ответственностью. Виды:
                    group  — организационный: только дети, своего кода
                             и портов нет;
                    leaf   — лист: порты, гарантии, код, тесты;
                    entry  — единственный лист с main() и «корнем
                             сборки», который создаёт все листья и
                             соединяет их по связям схемы;
                    shared — общий модуль (типы, логирование, зонды).
  Порт            Вход (in), выход (out) или предоставляемая функция
                  (fn) листа.
  Связь           Типизированное ребро между листьями (use — от листа
                  к shared-блоку): data, event, call, state, use
                  (раздел 3.5).
  Поднятая связь  Связь листьев, показанная на верхнем уровне между их
                  предками (раздел 3.6).
  Карточка        Файл block.ksl в папке блока.
  Контракт        Интерфейс листа (api/*.hpp) + гарантии из карточки +
                  контрактные тесты. После утверждения замораживается.
  KSL             Karkas Schema Language — компактный построчный формат
                  карточек, тикетов, отчётов и видов (раздел 4).
  Индекс          База SQLite, производная от карточек и кода, для
                  быстрых запросов. Источник правды — карточки и код в git.
  Вид (view)      Компактный текст части схемы для модели, уровни
                  L0/L1/L2.
  Тикет           Запись о задаче или баге; спускается по схеме и
                  дополняется на каждом уровне (раздел 10).
  Отчёт (report)  Ответ агента наверх фиксированной формы.
  Изменение       Предложение изменить схему (@change); ждёт утверждения.
  Оркестратор     Сильная модель верхнего уровня; видит идею и схему,
                  не видит код.
  Архитектор      Сильная модель, проектирующая схему сверху вниз.
  Навигатор       Агент составного блока: выбирает, в какой подблок
                  спуститься. Кода не видит.
  Исполнитель     Агент листа: читает и пишет код только в своей папке.
  Тестировщик     Агент, пишущий контрактные тесты по карточке и
                  интерфейсу, не видя реализации.
  Маршрутизатор   Алгоритм выбора уровня модели под задачу.
  Эскалация       Передача задачи более сильной модели или человеку.
  Дрейф           Расхождение схемы и кода.
  Зонд (probe)    Лёгкий счётчик на связи в коде целевого проекта.
  Уровень (tier)  Класс модели по цене и силе: strong, medium, cheap,
                  local.


==========================================================================
3. МОДЕЛЬ ДАННЫХ: БЛОКИ, ПОРТЫ, СВЯЗИ
==========================================================================

3.1 Общая форма
  Схема = дерево + граф.
  - Дерево задаёт вложенность: проект (project.ksl) → блоки верхнего
    уровня → … → листья. Глубина 2–5 уровней, у составного блока 2–9
    детей.
  - Граф задаёт связи между портами ЛИСТЬЕВ, то есть там, где реально
    есть код. Связь может соединять листья из разных ветвей дерева.
  - Идентификатор блока — путь через точку: stream.ring. Он совпадает с
    путём папки: blocks/stream/ring/.

3.2 Поля блока
  id       путь блока, уникален
  kind     group | leaf | entry | shared
  purpose  одна фраза на английском: зачем блок существует
  thread   поток исполнения (main, reader, audio_rt, any …); leaf, entry, shared
  est      оценка сложности S | M | L (ставит архитектор)
  ports    входы, выходы, функции (3.4); только leaf, entry, shared
  links    входящие связи; объявляются в карточке потребителя (3.5)
  inv      гарантии, каждая — одна строка (3.8)
  hist     краткая история ошибок и решений (3.10)
  status   хранится ТОЛЬКО в индексе, заполняет программа:
           design | api_frozen | tests_ready | implemented | passing |
           failing | drift | needs_review

3.3 Почему у составных блоков нет своих портов
  Порты групп пришлось бы поддерживать вручную, и они расходились бы с
  портами листьев. Поэтому связи объявляются только между листьями, а
  виды верхних уровней программа строит «поднятием» связей (3.6). Код,
  который создаёт и соединяет все листья, один — в блоке entry («корень
  сборки», composition root). Группы — чистая организация: папка,
  карточка с purpose и дети.

3.4 Порты
  in  <name> <Type>            вход данных или событий
  out <name> <Type>            выход данных или событий
  fn  <name>(<params>) -> <R>  функция, которую лист предоставляет
  Тип — имя, объявленное в C++ в api/ блока-поставщика или в
  shared.types. KSL не описывает внутренность типов (это не IDL): он
  ссылается на имена, а существование имён проверяет программа
  (раздел 8).

3.5 Связи
  Объявляются в карточке ПОТРЕБИТЕЛЯ (того, кто получает или вызывает):
    data, event  атрибуты строки входа:
                 in <имя> <Тип> from=<блок>:<порт> link=data|event [via= sync= rate=]
                 (link= по умолчанию data)
    call         call <блок>:<fn>
    use          use <shared-блок>
    state        state <имя> <Тип> with=<блок>

  Вид    Смысл                                          Пример
  data   поток данных от out-порта к in-порту           кадры звука
  event  событие или сигнал, редкое и асинхронное       нажата пауза
  call   синхронный вызов fn другого листа              open(path)
  state  общее изменяемое состояние — нежелательно,     общий счётчик
         всегда помечается как риск
  use    зависимость от shared-блока                    логирование

  Атрибуты связи:
  via=   механизм передачи: ring_buffer(N), queue, mutex, atomic, direct
  sync=  синхронизация при пересечении потоков: lock_free, mutex, none
  rate=  ожидаемая частота или объём: 48k/s, 30fps (для зондов и отладки)

  Правило: если потоки поставщика и потребителя различаются и ни один из
  них не any, атрибут via= ДОЛЖЕН быть указан, иначе предупреждение W01.

3.6 Поднятие связей на верхние уровни
  На виде блока X связь между листьями A и B показывается между теми
  детьми X, которые содержат A и B (если это разные дети). Одинаковые
  поднятые связи схлопываются в одну со счётчиком ×N. Статус составного
  блока равен худшему статусу среди его потомков. Всё это считает
  программа.

3.7 Общие модули (shared)
  Лежат в blocks/shared/. Связи use к ним скрыты на видах L0/L1 и на
  картинке (включаются переключателем), чтобы не тянуть линии от каждого
  блока. Изменение интерфейса shared-блока — всегда изменение схемы,
  которое утверждает человек.

3.8 Гарантии (инварианты)
  Короткие проверяемые утверждения о поведении листа:
    inv never loses or duplicates frames, including at wraparound
    inv push and pop never block
  Из каждой гарантии тестировщик делает минимум один контрактный тест.

3.9 Критерии листа (когда остановить разбиение)
  Блок становится листом, если выполнено всё:
  - назначение умещается в одну фразу без «и»;
  - ожидаемая реализация ≤ ~400 строк;
  - ≤ 6 портов;
  - один поток исполнения (пересечения потоков — только на портах);
  - тестируется через порты с заглушками соседей.

3.10 История блока
    hist T-0042 drop at wraparound -> mask index with cap-1
  Пишет ПРОГРАММА по отчёту исполнителя, а не модель. В карточке
  хранятся последние 10 записей; более старые сворачиваются в одну
  строку-итог.


==========================================================================
4. ЯЗЫК СХЕМЫ KSL (Karkas Schema Language)
==========================================================================

4.1 Почему не новый язык программирования
  - Модель читает текст токенами. Привычные английские слова (in, out,
    use, purpose) стоят около одного токена и понятны без обучения.
    Незнакомый синтаксис пришлось бы объяснять спецификацией в каждом
    запросе — это лишние токены.
  - Русский текст обычно занимает больше токенов, чем английский. Поэтому
    директивы, идентификаторы и строки purpose/inv пишутся на
    английском.
  - Построчный формат: один факт — одна строка. Легко разбирать, легко
    дополнять, понятный diff в git, легко отрезать лишнее при выдаче
    модели.
  - Один синтаксис для всего: проект, карточки, тикеты, отчёты,
    изменения, виды.

4.2 Лексика
  - Кодировка UTF-8, окончания строк LF.
  - Комментарий: # до конца строки (вне кавычек).
  - Заголовок записи — строка, начинающаяся с @: @project, @block,
    @ticket, @report, @change, @view.
  - Остальные строки: <директива> <аргументы>.
  - Идентификатор: [a-z][a-z0-9_]*. Путь блока: ident(.ident)*.
    Ссылка на порт: <путь_блока>:<порт>.
  - Атрибут: key=value (value без пробелов или в кавычках "…").
  - Свободный текст до конца строки, без кавычек: purpose, inv, idea,
    rule, note, symptom, fact, reason, cause, fix, tests, verify, а также
    hist (после id тикета).
  - Секция внутри записи: строка «--- имя» (например «--- trail»).
  - Отступы не значимы, пустые строки игнорируются.

4.3 Файл проекта: project.ksl (в корне целевого проекта)
    @project wavkit
    idea    CLI audio pipeline: read WAV files, apply effects, mix tracks, write WAV
    lang    cpp
    build   cmake-ninja
    std     c++20
    test    doctest
    rule    blocks talk only through api/ headers
    rule    no exceptions across block boundaries, use Result<T>

4.4 Карточка блока: block.ksl (в папке блока)
  Лист:
    @block stream.ring
    purpose lock-free single-producer single-consumer ring of audio frames
    kind    leaf
    thread  any
    est     M
    in      push   Frame[]   from=stream.pump:frames link=data sync=lock_free rate=48k/s
    out     pop    Frame[]
    fn      capacity() -> size_t
    fn      fill() -> size_t
    use     shared.types
    use     shared.probe
    inv     never loses or duplicates frames, including at wraparound
    inv     push and pop never block
    inv     fill() is always within [0, capacity()]
    hist    T-0042 drop at wraparound -> mask index with cap-1

  Составной блок (дети определяются по подпапкам):
    @block stream
    purpose move frames from reader thread to processing
    kind    group

  Директивы карточки:
    Директива  Где                 Кратность  Смысл
    purpose    все                 1          назначение (обязательно)
    kind       все                 1          group|leaf|entry|shared
    thread     leaf/entry/shared   0..1       поток исполнения
    est        leaf/entry          0..1       S|M|L
    in, out    leaf/entry/shared   0..N       порты данных и событий
    fn         leaf/shared         0..N       предоставляемые функции
    call       leaf/entry          0..N       вызов fn другого листа
    use        leaf/entry          0..N       зависимость от shared
    state      leaf                0..N       общее состояние (риск)
    inv        leaf/shared         0..N       гарантии
    note       все                 0..3       заметка человека
    hist       leaf/entry          0..10      история (пишет программа)
  Статус в карточке не пишется: он живёт только в индексе.
  Пути к файлам не пишутся: код блока по соглашению лежит в его папке
  (api/, impl/, tests/, mocks/).

4.5 Формальная грамматика (EBNF)
  file      = { record } ;
  record    = header NL { line | section } ;
  header    = "@" kind_kw WS ( path | rec_id ) { WS attr } ;
  rec_id    = ( "T" | "C" ) "-" digit { digit } ;   (* T-0042, C-0003 *)
  kind_kw   = "project" | "block" | "ticket" | "report" | "change" | "view" ;
  section   = "---" WS ident NL { line | diff_line } ;
  line      = directive { WS arg } [ comment ] NL ;
  directive = ident | "L" digit ;        (* L0, L1 … — записи trail *)
  arg       = attr | portref | path | type | sig | text ;
  attr      = ident "=" ( word | quoted ) ;
  portref   = path ":" ident ;
  path      = ident { "." ident } ;
  type      = typename [ "[]" ] ;
  sig       = ident "(" [ params ] ")" [ "->" typename ] ;
  text      = ? остаток строки для директив свободного текста ? ;
  comment   = "#" ? до конца строки ? ;
  diff_line = ( "+" | "-" | "~" ) WS ? строка KSL ? ;  (* только в секции diff *)

  Парсер — рукописный рекурсивный спуск, один проход. Таблица директив
  задаёт для каждой: в каких записях допустима, кратность, вид
  аргументов. Ошибки — с файлом, строкой и колонкой.

4.6 Правила проверки (karkas check)
  Ошибки (E) блокируют работу агентов:
    E01 id в @block не совпадает с путём папки
    E02 нет purpose или kind
    E03 from= или call ссылается на несуществующий блок или порт
    E04 связь data/event: у поставщика нет out-порта с таким именем
    E05 call ссылается не на fn
    E06 у group нет детей; у leaf/entry есть дети; entry не ровно один
    E07 повтор имени порта в одном блоке
    E08 директива недопустима для этого вида блока
  Предупреждения (W) показываются, но не блокируют:
    W01 пересечение потоков без via=
    W02 связь state (общее изменяемое состояние)
    W03 у group больше 9 детей или глубина больше 5
    W04 purpose длиннее 100 символов или содержит " and "
    W05 цикл вызовов call между листьями
    W06 лист без inv

4.7 Виды для модели (что реально попадает в контекст)
  Программа рендерит часть схемы в компактный текст. Три уровня.

  L0 — обзор проекта (для оркестратора), связи подняты (3.6):
    @view root level=0
    idea CLI audio pipeline: read WAV files, apply effects, mix tracks, write WAV
    app     entry  CLI args, composition root, run loop               ok
    io      group  WAV file input/output (2)                          ok
    stream  group  move frames from reader thread to processing (2)   FAIL 1
    dsp     group  effect chain applied to frames (4)                 ok
    mix     leaf   mix N tracks with per-track gain, clip-safe        ok
    --- links
    io     -data-> stream
    stream -data-> dsp     sync=lock_free thr=any->main
    dsp    -data-> mix
    mix    -data-> io

  L1 — составной блок (для навигатора): дети одной строкой, внутренние
  связи, внешние связи, сводка зондов:
    @view stream level=1
    purpose move frames from reader thread to processing
    stream.pump  leaf  reader thread that moves frames from io.reader into stream.ring  thr=reader  ok
    stream.ring  leaf  lock-free single-producer single-consumer ring of audio frames   thr=any     FAIL 1
    --- links
    stream.pump:frames -data-> stream.ring:push  sync=lock_free rate=48k/s thr=reader->any
    --- external
    in   io.reader:frames -> stream.pump:src
    out  stream.ring:pop -> dsp.chain:in  sync=lock_free thr=any->main
    --- probes
    stream.pump->stream.ring fill min=0 avg=3810 max=8192 anomaly=min0

  L2 — лист (для исполнителя и тестировщика): полная карточка блока +
  сигнатуры портов тех соседей, с которыми он связан:
    @view stream.ring level=2
    (карточка stream.ring целиком)
    --- neighbors
    stream.pump  out frames Frame[]  thr=reader
    dsp.chain    in  in     Frame[]  thr=main

  Целевые размеры (проверяются тестами на эталонных проектах):
    L0 ≤ 800 токенов при ≤ 9 блоках верхнего уровня;
    L1 ≤ 600 токенов; L2 ≤ 1200 токенов без кода.
  Связи use к shared на L0/L1 скрыты и выдаются только по запросу.

4.8 Каноническое оформление
  Писатель KSL выравнивает директивы по ширине 8 символов и соблюдает
  фиксированный порядок: purpose, kind, thread, est, in, out, fn, call,
  use, state, inv, note, hist. Поэтому diff в git стабилен, а повторная
  запись неизменённой карточки даёт тот же файл байт в байт.


==========================================================================
5. РАСКЛАДКА ЦЕЛЕВОГО ПРОЕКТА НА ДИСКЕ
==========================================================================

5.1 Принцип: блок = папка
  Структура папок повторяет дерево схемы один к одному. Путь к файлу сам
  говорит, где блок находится в схеме. Человек видит порядок, агент
  получает естественные границы доступа.

5.2 Пример
  wavkit/
  ├─ project.ksl
  ├─ karkas.toml                 настройки Karkas для проекта (прил. E)
  ├─ CMakeLists.txt              генерирует Karkas (5.5)
  ├─ cmake/user.cmake            ручные дополнения к сборке
  ├─ blocks/
  │  ├─ app/                     entry
  │  │  ├─ block.ksl
  │  │  ├─ impl/main.cpp
  │  │  ├─ impl/compose.cpp      корень сборки: создаёт и соединяет листья
  │  │  └─ tests/
  │  ├─ io/                      group
  │  │  ├─ block.ksl
  │  │  ├─ reader/               leaf
  │  │  │  ├─ block.ksl
  │  │  │  ├─ api/reader.hpp     контракт (заморожен)
  │  │  │  ├─ impl/reader.cpp
  │  │  │  ├─ tests/contract/    пишет тестировщик, не видя impl/
  │  │  │  ├─ tests/unit/        может писать исполнитель
  │  │  │  └─ mocks/             заглушки соседей
  │  │  └─ writer/ …
  │  ├─ stream/   (pump/, ring/)
  │  ├─ dsp/      (chain/, gain/, lowpass/, echo/)
  │  ├─ mix/
  │  └─ shared/   (types/, log/, probe/)
  ├─ tests/integration/          тесты групп и всего проекта
  └─ .karkas/                    служебная папка (5.4)

5.3 Содержимое папки листа
  block.ksl  карточка (обязательна).
  api/       публичный интерфейс — заголовки .hpp. Пишется при
             проектировании, после утверждения человеком замораживается
             (хэш хранится в индексе). Изменение api/ = изменение
             контракта → эскалация и утверждение человеком.
  impl/      реализация.
  tests/     contract/ (тестировщик), unit/ (исполнитель).
  mocks/     заглушки соседей: генерируются по их api/ или пишутся
             тестировщиком.

5.4 Служебная папка .karkas/
  index.db     индекс SQLite                     не в git, пересоздаётся
  tickets/     T-0001.ksl …                      в git (история проекта)
  changes/     C-0001.ksl … изменения схемы      в git
  runs/        журналы запусков агентов, JSONL   не в git (большие)
  probes/      данные зондов                     не в git
  layout/      ручные позиции блоков на картинке в git
  cache/       кэш раскладки и анализа кода      не в git
  karkas.log   журнал программы                  не в git
  Karkas создаёт .karkas/.gitignore с нужными исключениями.

5.5 Сборка целевого проекта: блок = цель CMake
  Karkas генерирует CMakeLists.txt целевого проекта из схемы:
  - leaf и shared → add_library(<id_через_подчёркивания> STATIC impl/*.cpp)
    (shared без impl/ → INTERFACE);
  - target_include_directories(<цель> PUBLIC api PRIVATE impl);
  - каждая связь потребителя с поставщиком →
    target_link_libraries(<потребитель> PRIVATE <поставщик>);
  - group → INTERFACE-библиотека, объединяющая потомков (удобно для
    сборки и тестов поддерева);
  - entry → add_executable, связан со всеми листьями, которые соединяет;
  - тесты листа → отдельный исполняемый файл + add_test с метками
    (LABELS) = id блока и id всех его предков, чтобы запускать
    «ctest -L stream.ring» или «ctest -L stream».
  Главное следствие: лист физически не может подключить заголовок блока,
  с которым у него нет связи в схеме, — компилятор не найдёт путь
  include. Это основная защита от тихого расхождения схемы и кода.
  CMakeLists.txt помечен как сгенерированный, ручные правки запрещены
  (их ловит проверка D07). Пользовательские дополнения — в
  cmake/user.cmake, который подключается в конце.

5.6 Источник правды
  Источник правды — текстовые карточки и код в git. Индекс SQLite —
  производная, его можно удалить в любой момент. GUI и агенты ничего не
  пишут в индекс напрямую: любое изменение схемы = изменение файла .ksl
  → переиндексация.

5.7 Правила для интерфейсов (C++)
  - Интерфейс листа — абстрактный класс (struct IName { virtual … = 0; })
    и/или простые структуры данных без зависимостей реализации.
  - Зависимости передаются через конструктор (внедрение зависимостей).
    Блок entry в compose.cpp создаёт листья и соединяет их.
  - Поэтому в тестах любого соседа можно подменить заглушкой.
  - Исключения не пересекают границы блоков: Result<T> или коды ошибок.

==========================================================================
6. АРХИТЕКТУРА ПРОГРАММЫ KARKAS
==========================================================================

6.1 Слои
  человек → karkas-gui / karkas (CLI)        внешний агент → karkas mcp
                        \                              /
           kk_agents   kk_layout   kk_runner   kk_metrics   kk_mcp
                        |                      |
                  kk_llm      kk_index  ←  kk_code
                                  |
                               kk_core
  Внизу — модель данных без внешних зависимостей, выше — данные и
  анализ, ещё выше — сервисы, наверху — приложения.

6.2 Модули (CMake-цели) и зависимости
  kk_core     модель данных, парсер и писатель KSL, валидатор, Result,
              утилиты путей и хэшей.
              Зависит: стандартная библиотека, fmt.
  kk_index    SQLite-индекс, полная и инкрементальная индексация,
              запросы, рендер видов L0/L1/L2.
              Зависит: kk_core, sqlite3, xxhash.
  kk_code     анализ кода через tree-sitter, проверки дрейфа,
              генерация CMake, заглушек, зондов, заготовок листа.
              Зависит: kk_core, kk_index, tree-sitter, tree-sitter-cpp.
  kk_runner   запуск cmake/ninja/ctest как подпроцессов, таймауты,
              очищенное окружение, сжатие логов сборки.
              Зависит: kk_core, reproc.
  kk_llm      клиенты моделей: Anthropic Messages API и
              OpenAI-совместимый; tool use, метки кэша, учёт usage,
              повторы, запись и воспроизведение ответов.
              Зависит: kk_core, libcurl, nlohmann_json.
  kk_metrics  журнал запусков, расчёт денег, отчёты.
              Зависит: kk_core, kk_index.
  kk_agents   роли, цикл агента, песочница, тикеты, маршрутизатор,
              эскалация, планировщик заданий.
              Зависит: kk_core, kk_index, kk_code, kk_runner, kk_llm,
              kk_metrics.
  kk_mcp      MCP-сервер (stdio, JSON-RPC 2.0).
              Зависит: kk_core (формат тикетов), kk_index,
              kk_runner (для run_tests).
  kk_layout   раскладка графа через Graphviz, кэш позиций.
              Зависит: kk_core, kk_index, graphviz (cgraph, gvc).
  karkas      CLI. Зависит от всех библиотек, кроме GUI; CLI11.
  karkas-gui  GUI. Зависит от всех + Dear ImGui, GLFW, OpenGL,
              imgui-node-editor, ImGuiColorTextEdit.
  Правила: зависимости только сверху вниз, без циклов; kk_core не знает
  ни про SQLite, ни про сеть; GUI можно не собирать (KARKAS_GUI=OFF).

6.3 Четыре основных потока
  Проектирование: идея → архитектор → project.ksl и карточки верхнего
    уровня → утверждение человеком → раскрытие блоков → api/*.hpp
    листьев → утверждение → тестировщики пишут контрактные тесты →
    генерация CMake → исполнители пишут impl/ → тесты → корень сборки
    → интеграционные тесты.
  Разработка: задача человека → оркестратор (вид L0) → тикет → спуск →
    исполнители → тесты → отчёт вверх → регрессия соседей.
  Отладка: симптом (от человека или упавшего теста) + факты → тикет →
    спуск по связям с дополнением → исполнитель находит причину →
    отчёт вверх → регрессия → закрытие.
  Отображение: изменение .ksl или кода → inotify → переиндексация →
    GUI перерисовывает (раскладка из кэша или пересчёт Graphviz).

6.4 Поточность и параллельность
  - Пул потоков для агентов: независимые листья обрабатываются
    параллельно (лимит max_parallel_agents, по умолчанию 2).
  - Сборки и тесты целевого проекта — отдельный лимит
    max_parallel_builds (по умолчанию 1): компиляция грузит процессор,
    а запросы к модели — сеть.
  - Индекс: SQLite в режиме WAL, один писатель (поток индексатора),
    много читателей.
  - CLI и GUI могут работать одновременно: GUI видит изменения через
    inotify на .karkas/ и PRAGMA data_version.
  - Один тикет в один момент обрабатывает один агент: блокировка файлом
    .karkas/tickets/T-NNNN.lock.
  - Поток GUI никогда не ждёт сеть или диск: раскладка и запросы идут в
    фоне, результаты передаются через очередь.

6.5 Конфигурация и секреты
  Порядок поиска: <проект>/karkas.toml, затем
  ~/.config/karkas/config.toml. Ключ API берётся ТОЛЬКО из переменной
  окружения ANTHROPIC_API_KEY и никогда не пишется в файлы и журналы.
  Пример конфигурации — приложение E.

6.6 Ошибки и журналы
  - Ошибки — std::expected<T, kk::Error>; исключения не выходят за
    границы модулей.
  - Журнал — spdlog: файл .karkas/karkas.log и stderr. В режиме MCP
    stdout занят протоколом, поэтому журнал строго в stderr или файл.
  - Каждая ошибка KSL содержит файл, строку и колонку.

6.7 Форматы данных
  KSL     карточки, проект, тикеты, отчёты, изменения, виды
  SQLite  индекс (производный)
  JSONL   журналы запусков агентов, данные зондов, результаты замеров
  TOML    конфигурация
  JSON    обмен с API моделей и MCP

7. ИНДЕКС И ЗАПРОСЫ К СХЕМЕ
==========================================================================

7.1 Схема базы (SQLite)
  PRAGMA journal_mode=WAL;  PRAGMA foreign_keys=ON;

  CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT);  -- версия схемы БД

  CREATE TABLE blocks(
    id TEXT PRIMARY KEY, parent TEXT, kind TEXT NOT NULL,
    purpose TEXT NOT NULL, thread TEXT, est TEXT,
    depth INTEGER NOT NULL, dir TEXT NOT NULL,
    card_hash TEXT NOT NULL, api_hash TEXT, api_frozen_hash TEXT,
    status TEXT NOT NULL DEFAULT 'design', updated_at INTEGER);

  CREATE TABLE ports(
    block TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
    name TEXT NOT NULL, dir TEXT NOT NULL,          -- in | out | fn
    type TEXT, signature TEXT, line INTEGER,
    PRIMARY KEY(block, name));

  CREATE TABLE links(
    id INTEGER PRIMARY KEY,
    src_block TEXT NOT NULL, src_port TEXT,
    dst_block TEXT NOT NULL, dst_port TEXT,
    kind TEXT NOT NULL,                             -- data|event|call|state|use
    via TEXT, sync TEXT, rate TEXT,
    thread_src TEXT, thread_dst TEXT,               -- копии для быстрых запросов
    declared_in TEXT NOT NULL, line INTEGER);

  CREATE TABLE invariants(block TEXT, idx INTEGER, text TEXT,
    PRIMARY KEY(block, idx));
  CREATE TABLE history(block TEXT, ticket TEXT, summary TEXT, ts INTEGER);
  CREATE TABLE files(path TEXT PRIMARY KEY, block TEXT,
    role TEXT,                                      -- api|impl|test|mock
    hash TEXT, lines INTEGER);
  CREATE TABLE symbols(id INTEGER PRIMARY KEY, file TEXT, block TEXT,
    name TEXT, kind TEXT, line INTEGER, exported INTEGER);
  CREATE TABLE code_refs(from_block TEXT, from_file TEXT, line INTEGER,
    to_block TEXT, to_role TEXT, kind TEXT);        -- include | call
  CREATE TABLE drift(block TEXT, code TEXT, severity TEXT,
    message TEXT, file TEXT, line INTEGER);
  CREATE TABLE tickets(id TEXT PRIMARY KEY, kind TEXT, status TEXT,
    origin TEXT, current_block TEXT, created_at INTEGER, closed_at INTEGER);
  CREATE TABLE runs(id INTEGER PRIMARY KEY, ticket TEXT, role TEXT,
    block TEXT, provider TEXT, model TEXT, tier TEXT, attempt INTEGER,
    input_tokens INTEGER, output_tokens INTEGER,
    cache_write_tokens INTEGER, cache_read_tokens INTEGER,
    cost_usd REAL, duration_ms INTEGER, steps INTEGER,
    outcome TEXT, ts INTEGER);
  CREATE TABLE probes(link_id INTEGER, metric TEXT, n INTEGER,
    min REAL, max REAL, avg REAL, last REAL, run TEXT, ts INTEGER);
  CREATE VIRTUAL TABLE search USING fts5(block, purpose, inv, hist);

  Индексы: links(src_block), links(dst_block), blocks(parent),
  files(block), code_refs(from_block), runs(ticket), runs(block).

7.2 Индексация
  - Полная: обход blocks/, разбор всех block.ksl, хэши xxh3 карточек и
    файлов кода, анализ кода (раздел 8), заполнение таблиц в одной
    транзакции.
  - Инкрементальная: по хэшам меняется только изменившееся. Источники
    событий: inotify (karkas index --watch, GUI) или явный вызов после
    каждого действия агента.
  - Цель (вместе с анализом кода, раздел 8): проект на 50 блоков и
    20 тыс. строк — полная индексация < 2 с, инкрементальная < 100 мс
    на слабом двухъядерном ноутбуке.

7.3 Запросы (API kk_index; они же инструменты агентов и MCP)
  overview()                          вид L0
  view(block, level)                  вид L1 или L2
  children(block)                     дети, по строке на каждого
  neighbors(block, kind?, dir?)       связанные листья (in/out/both)
  dependents(block)                   кто зависит от его интерфейса
  path(a, b)                          цепочка связей между блоками
  writers(block:port), readers(…)     кто пишет в порт и кто читает
  by_thread(thread)                   листья, работающие в потоке
  search(text)                        полнотекстовый поиск: purpose, inv, hist
  history(block, n)                   последние записи истории
  status(block?)                      статусы, упавшие тесты, дрейф
  probes(block | link)                сводка зондов (числа, не логи)
  drift(block?)                       отчёт о расхождениях
  Все запросы возвращают компактный KSL-текст (для модели) или
  структуры C++ (для GUI). Обход поддеревьев — рекурсивные CTE SQLite.

8. АНАЛИЗ КОДА И КОНТРОЛЬ ДРЕЙФА
==========================================================================

8.1 Что извлекается через tree-sitter (грамматика tree-sitter-cpp)
  - директивы #include и к какому блоку и роли (api или impl) они ведут;
  - объявления в api/: классы, структуры, перечисления, свободные
    функции, псевдонимы типов — с номерами строк;
  - определения функций в impl/;
  - вызовы функций по именам — приблизительно сопоставляются с
    экспортируемыми символами связанных блоков.
  Почему tree-sitter: быстрый, работает инкрементально и терпим к
  незаконченному коду. Точный анализ (clangd или libclang) — позже, по
  необходимости.

8.2 Проверки (детерминированные, без модели)
  D01 include из impl/ другого блока — ошибка всегда
  D02 include из api/ блока, с которым нет связи в схеме — ошибка
      (кроме entry: ему разрешены api/ всех листьев, которые он соединяет)
  D03 тип порта не найден среди объявлений api/ поставщика или shared.types
  D04 fn из карточки не найдена в api/ (по имени; в v1 сигнатура
      сверяется мягко — по числу параметров)
  D05 api/ изменился после заморозки (api_hash ≠ api_frozen_hash) —
      изменение контракта, нужно утверждение
  D06 файл кода вне папок блоков («сирота»)
  D07 сгенерированный CMakeLists.txt изменён вручную
  D08 лист без контрактных тестов
  D09 вызов функции блока, с которым нет связи call (эвристика,
      предупреждение)
  Результат — таблица drift и текстовый отчёт:
    drift E D02 stream.pump impl/pump.cpp:12 includes dsp.chain api without link

8.3 Генерация (детерминированная)
  karkas gen cmake  CMakeLists.txt целевого проекта (5.5)
  karkas gen mocks  заглушки по api/ соседей: класс, наследующий
                    интерфейс, с записью вызовов и настраиваемыми
                    ответами (шаблон в templates/target/)
  karkas gen probe  shared/probe/karkas_probe.hpp (12.5)
  karkas gen skel   пустые impl/ и tests/ по карточке нового листа
  Заголовки api/ НЕ генерируются из KSL (KSL не IDL). Их пишет архитектор
  при раскрытии блока, человек утверждает, после чего они
  замораживаются.

9. АГЕНТЫ: РОЛИ, КОНТЕКСТ, ИНСТРУМЕНТЫ
==========================================================================

9.1 Роли
  Роль         Уровень        Когда работает                   Код
  Архитектор   strong         проектирование, раскрытие,       пишет только api/
                              перестройка схемы
  Оркестратор  strong*        каждая задача и каждый баг       не видит
  Навигатор    medium         спуск через составной блок       не видит
  Исполнитель  по маршрутиз.  работа внутри листа              свой блок +
                                                               api/ соседей
  Тестировщик  cheap/medium   контрактные тесты листа          api/ и карточка,
                                                               НЕ impl/
  * Оркестратор видит только схему, поэтому замерами СЛЕДУЕТ проверить,
    не хватает ли ему уровня medium: это может дать заметную экономию.

  Агенты не живут постоянно. Каждый запуск — новый изолированный
  контекст, который программа собирает из карточек, видов, тикета и
  файлов. Постоянно только знание на диске.

  Сводки «снизу вверх» собирает программа, а не модели: purpose детей,
  статусы, история и зонды уже лежат в карточках и индексе. Смысл
  блоков фиксируется при проектировании, поэтому пересказывать его
  моделью при каждом изменении не нужно (экономия токенов, принцип П7).
  Модели нужны для сводок только в одном случае — при импорте
  существующего проекта (этап 11), когда карточек ещё нет: тогда
  дешёвые модели описывают папки снизу вверх, а человек утверждает
  результат.

9.2 Что попадает в контекст каждой роли
  Архитектор: идея, правила проекта (rule), вид родителя и соседей
    раскрываемого блока, критерии листа, справка KSL.
  Оркестратор: idea (одна строка), вид L0 со статусами, тикет (вид
    пути), заголовки последних тикетов.
  Навигатор: purpose родителя, вид L1 своего блока, сводка зондов на
    внутренних связях, тикет (вид пути).
  Исполнитель: вид L2 своего листа; api/ своего листа; api/ связанных
    соседей (только заголовки); impl/ и tests/unit/ своего листа (мелкие
    файлы сразу, крупные по запросу через read_file); тикет (вид пути);
    сжатые результаты последней сборки и тестов; hist листа.
    НЕ видит: идею проекта, схему целиком, чужой impl/.
  Тестировщик: карточка (purpose, порты, inv), api/ листа, api/
    соседей, существующие mocks/. НЕ видит impl/: проверяет обещания, а
    не код.

9.3 Инструменты ролей (tool use)
  Оркестратор и навигатор (без доступа к файлам):
    view · neighbors · dependents · path · search · history · status ·
    probes · dispatch(block, entry) · ask(block, question) ·
    run_tests(block) · propose_change(ksl_diff) · close(verdict) ·
    report(not_here) — только навигатор
  Исполнитель (в песочнице листа):
    read_file · list_dir · grep · write_file · edit_file · build ·
    test(filter?) · report
  Тестировщик:
    read_file (api/, mocks/, карточки) · write_file (tests/contract/,
    mocks/) · build · test · report
  Архитектор:
    view · search · write_card(block, ksl) · write_api(block, file,
    code) · propose_change
  Примеры описаний инструментов — приложение C.

9.4 Цикл агента
  1. Программа собирает контекст роли (9.2): постоянная часть
     (инструкции роли, справка KSL, описания инструментов) + переменная
     часть (вид, тикет, файлы).
  2. Запрос к модели через kk_llm. Если stop_reason = tool_use —
     выполнить инструменты в песочнице, добавить tool_result, повторить.
  3. Остановка: вызван report, dispatch, close или propose_change;
     превышен лимит шагов (max_steps); превышен бюджет токенов на
     запуск; истёк таймаут.
  4. Каждый шаг пишется в .karkas/runs/<время>-<роль>-<блок>.jsonl,
     итог — строкой в таблицу runs.
  5. Отчёт разбирает ПРОГРАММА (запись @report) и применяет: статус
     блока, запись hist, продвижение тикета.

9.5 Песочница исполнителя (обязательные требования)
  - Все пути нормализуются (std::filesystem::weakly_canonical) и
    проверяются на вхождение в разрешённые корни. «..», абсолютные пути
    и символические ссылки наружу — отказ.
  - Запись: только impl/ и tests/unit/ своего листа (тестировщику —
    tests/contract/ и mocks/). Попытка записи в api/ — отказ с
    подсказкой «report status=needs_contract_change».
  - Чтение: свой лист + api/ блоков, с которыми есть связь, + api/
    shared-блоков.
  - build и test запускаются через kk_runner с таймаутом и очищенным
    окружением: ключи API и другие секреты процессам целевого проекта
    НЕ передаются.
  - Позже (по желанию): запуск тестов в bubblewrap (bwrap) без сети.

9.6 Структура запроса и кэширование
  Кэш Claude API учитывает порядок tools → system → messages и
  кэширует весь префикс до метки cache_control. Изменение описаний
  инструментов сбрасывает весь кэш. Поэтому порядок частей:
    [tools]    описания инструментов роли — неизменны между запусками
    [system]   инструкции роли + справка KSL                ← метка кэша
    [user 1]   стабильный контекст листа (вид, api/)        ← метка кэша
    [user 2]   тикет + задание (меняется)
    [далее]    шаги tool use
  Внутри одного цикла история шагов растёт; метку кэша СЛЕДУЕТ
  переносить на последний стабильный блок, чтобы каждый следующий шаг
  читал предыдущие из кэша.
  Ограничения: у каждой модели есть минимальная длина кэшируемого
  префикса, более короткие префиксы не кэшируются. Короткие запросы
  навигатора могут не дотягивать до минимума — это нормально, они и так
  дешёвые; кэш важнее всего в длинных циклах исполнителя. Кэш по
  умолчанию живёт 5 минут (есть вариант на 1 час). Число меток на
  запрос ограничено (на момент написания — 4), а совпадения ищутся не
  дальше примерно 20 блоков содержимого назад от метки, поэтому в
  длинных циклах метку двигают вперёд на каждом шаге. Срабатывание
  проверять по полям usage: cache_creation_input_tokens и
  cache_read_input_tokens.
  Цены кэша: запись на 5 минут — ×1,25 от цены входа, на 1 час — ×2,
  чтение — ×0,1. Конкретные пороги и синтаксис сверять с документацией
  на момент реализации.

9.7 Шаблоны промптов
  Хранятся файлами templates/prompts/<роль>.txt с подстановками
  {{project_idea}}, {{view}}, {{ticket}}, {{api_files}} и т. п.
  Подстановщик — свой, простой. Промпты пишутся на английском (дешевле
  по токенам). Черновики — приложение B.

9.8 Клиент Claude API (kk_llm) — опорные детали
  - POST https://api.anthropic.com/v1/messages; заголовки x-api-key,
    anthropic-version: 2023-06-01, content-type: application/json.
  - Запрос: model, max_tokens, system (массив текстовых блоков, на
    последнем стабильном — cache_control {"type":"ephemeral"}), tools
    (name, description, input_schema), messages.
  - Ответ: content (блоки text и tool_use с id, name, input),
    stop_reason (end_turn, tool_use, max_tokens …), usage
    (input_tokens, output_tokens, cache_creation_input_tokens,
    cache_read_input_tokens).
  - Результат инструмента возвращается сообщением роли user с блоком
    tool_result (tool_use_id, content, is_error).
  - Повторы: 429, 5xx и 529 — экспоненциальная пауза с учётом заголовка
    retry-after, не больше 5 попыток; 400 — без повторов, в журнал.
  - Таймаут запроса настраивается (по умолчанию 300 с). Стриминг в v1
    не нужен.
  - Одно соединение libcurl на поток с keep-alive.
  - OpenAI-совместимый клиент (локальные модели через Ollama и др.):
    POST {base_url}/chat/completions, инструменты в формате function
    calling. Качество вызова инструментов у локальных моделей разное,
    поэтому уровень local — только для простых задач и только после
    проверки замерами.
  - Имена моделей и цены задаются только в конфиге, не в коде. Детали
    API сверять с официальной документацией на момент реализации.


==========================================================================
10. ТИКЕТЫ: ПРОТОКОЛ ОБЩЕНИЯ АГЕНТОВ
==========================================================================

10.1 Принципы
  - Тикет — один файл .karkas/tickets/T-NNNN.ksl, который только
    дописывается. Единственное исключение — строка status в шапке: её
    обновляет программа.
  - Исходные данные (symptom и fact от источника) неизменны.
  - Каждый уровень спуска ДОБАВЛЯЕТ одну запись в секцию trail: что
    подозревает, что исключил, куда идёт дальше и почему.
  - Агенту выдаётся не весь файл, а «вид пути»: исходные данные +
    записи trail вдоль пути от корня до текущего блока. Гипотезы про
    уже исключённые соседние ветки в вид пути не попадают (в файле они
    остаются — для человека).
  - Результат идёт обратно вверх: дописывается в секцию result того же
    тикета.

10.2 Формат
  @ticket T-0042
  kind    bug                # bug | feature | change | question
  origin  tester             # human | tester | orchestrator
  status  open               # open | descending | fixing | verifying | closed | escalated
  symptom crackle in output after ~10 s of playback, worse with echo enabled
  fact    contract stream.ring/no_drop FAIL: dropped=37 of 480000 frames
  fact    probe stream.pump->stream.ring fill_min=0 at t=9.8s
  --- trail
  L0 orchestrator at=root   suspect=stream,dsp pick=stream difficulty=M why="frames dropped before dsp; ring runs empty"
  L1 navigator    at=stream suspect=stream.ring,stream.pump ruled_out=stream.pump pick=stream.ring why="pump rate ok 48k/s; drops at wraparound"
  L2 worker       at=stream.ring model=cheap attempt=1 outcome=fixed
  --- result
  status  fixed
  cause   off-by-one at wraparound: write index compared with capacity, not capacity-1
  fix     impl/ring.cpp:41 mask index with cap-1; unit test for wraparound added
  api     unchanged
  verify  stream.ring contract 5/5 pass; dsp.*, io.reader pass
  cost    in=21480 out=2930 cache_read=15210

10.3 Поля записи trail
  Запись оркестратора или навигатора:
    L<n> <роль> at=<блок> suspect=<блоки> ruled_out=<блоки> pick=<блок>
         difficulty=S|M|L why="<не больше 20 слов>"
  Запись исполнителя:
    L<n> worker at=<лист> model=<уровень> attempt=<n> outcome=<статус отчёта>
  Новый факт — отдельная строка «fact <текст>» сразу после записи своего
  уровня; в вид пути он попадает, если уровень лежит на пути.
  Ограничения: одна запись — не больше ~60 токенов; новых фактов на
  уровень — не больше двух, и только наблюдённые через инструменты
  (зонды, тесты), а не догадки.

10.4 Бюджет размера
  Вид пути при глубине 5 ДОЛЖЕН укладываться примерно в 600 токенов.
  Если факты разрастаются, программа оставляет исходные факты и
  последние новые, остальные сворачивает строкой
  «+N facts in ticket file».

10.5 Уточняющий вопрос вниз
  ask(block, question): программа запускает короткоживущего агента
  этого блока уровня cheap (для листа — исполнителя, для группы —
  навигатора) с его обычным контекстом и вопросом. Ответ не длиннее
  80 токенов дописывается в trail строкой
    answer at=<блок> "<ответ>"
  Спрашивающий получает только ответ, а не чужой контекст.

10.6 Отчёт исполнителя (@report)
  @report T-0042 from=stream.ring role=worker
  status  fixed     # fixed | done | failed | needs_contract_change | needs_info | not_here
  cause   …
  fix     …
  files   impl/ring.cpp, tests/unit/ring_test.cpp
  tests   contract 5/5 pass, unit 6/6 pass
  api     unchanged
  Статус not_here означает «причина не в моём блоке»: тикет возвращается
  на уровень выше с этой записью, и навигатор выбирает следующего
  подозреваемого.

10.7 Задачи и изменения схемы (@change)
  Тикеты задач (feature, change) подчиняются тем же правилам.
  Оркестратор раскладывает задачу на изменения блоков:
  - хватает существующих блоков и интерфейсов → тикеты в листья;
  - нужны новые блоки, порты или связи → запись @change → утверждение
    человеком → архитектор раскрывает → тестировщик → исполнитель.
  Формат:
    @change C-0003
    from    orchestrator T-0051
    reason  reverb requested; no existing block provides it
    status  pending          # pending | approved | rejected
    --- diff
    + @block dsp.reverb
    + purpose apply Schroeder reverb to frames
    + kind    leaf
    + fn      process(Frame[]) -> void
    ~ @block dsp.chain
    + call    dsp.reverb:process
  Строки «+» добавляются, «-» удаляются, «~» указывают, какую запись
  меняют. Применение — программой, после утверждения.

11. МАРШРУТИЗАЦИЯ МОДЕЛЕЙ И ЭСКАЛАЦИЯ
==========================================================================

11.1 Уровни моделей (настраиваются в karkas.toml)
  strong   например claude-opus-5-5     архитектор, оркестратор, трудные случаи
  medium   например claude-sonnet-5-5   навигатор, трудные листья, тестировщик L-блоков
  cheap    например claude-haiku-5-5    исполнитель и тестировщик по умолчанию
  local    модель через OpenAI-совместимый API (например, Ollama) —
           по желанию, только для простых задач
  Имена моделей — только в конфиге. При выходе новых моделей меняется
  конфиг, а не код.

11.2 Оценка сложности (балл 0–10, алгоритм, без модели)
  +3 est=L, +1 est=M
  +2 у листа есть связь с пересечением потоков (thread_src ≠ thread_dst)
  +2 есть связь state
  +1 impl/ больше 300 строк
  +1 за каждый неудачный тикет этого листа за последние 30 дней (макс. +2)
  +1 difficulty=M, +3 difficulty=L в записи вышестоящего агента
  Пороги по умолчанию: 0–3 → cheap, 4–6 → medium, 7 и выше → strong.

11.3 Эскалация
  - Исполнитель не прошёл тесты за 2 попытки → следующая попытка на
    уровень выше. Новой модели передаётся короткая выжимка прошлых
    попыток («что пробовали и почему не вышло»), чтобы не повторять.
  - Исчерпан бюджет шагов или токенов → эскалация.
  - needs_contract_change → наверх к оркестратору; изменение контракта
    утверждает человек.
  - Дважды not_here на одном уровне → тикет поднимается на уровень выше,
    навигатор следующего запуска получает уровень модели выше.
  - Неудача на уровне strong → тикет escalated; человек получает
    уведомление и всю историю.
  - Тесты важнее слов: если агент написал «исправлено», а тесты не
    прошли — не исправлено.

11.4 Самонастройка по данным
  После накопления статистики (таблица runs) маршрутизатор
  пересчитывает пороги: для каждой «корзины» признаков считается доля
  успеха уровня cheap с первой попытки. Если она ниже 60 %, такие задачи
  по умолчанию сразу идут на medium. Это простая статистика, а не
  обучение моделей.


==========================================================================
12. ТЕСТИРОВЩИКИ, КОНТРАКТЫ И НАБЛЮДАЕМОСТЬ
==========================================================================

12.1 Контрактные тесты
  - Пишет тестировщик по карточке (purpose, порты, inv) и api/, не видя
    impl/. Поэтому он проверяет обещание блока и не повторяет ошибок
    автора кода.
  - Фреймворк в целевом проекте — doctest (один заголовок, быстрая
    компиляция).
  - Каждая строка inv → минимум один тест, названный по этой гарантии.
  - Контрактные тесты пишутся ДО реализации, сразу после заморозки api/.
    Падение тестов на ещё не реализованном листе — норма.

12.2 Стенд листа
  Тест создаёт лист, подставляя вместо соседей заглушки из mocks/,
  подаёт искусственные входы и проверяет выходы и гарантии. Остальной
  проект не нужен — изоляция сохраняется.

12.3 Статусы приёмки
  Лист: design → api_frozen → tests_ready → implemented → passing
  (failing, drift и needs_review возможны в любой момент).
  Лист «готов», только когда его контрактные тесты проходят. Группа
  готова, когда готовы все потомки и проходят её интеграционные тесты
  (tests/integration/<id группы>/), которые пишет тестировщик уровня
  medium по видам L1 и api/ детей.

12.4 Регрессия после изменения
  Изменился только impl/ листа X:
    тесты X → интеграционные тесты групп-предков X.
  Изменился api/ листа X (после утверждения):
    тесты X → тесты всех dependents(X) → интеграционные тесты общих
    предков; зависимые листья получают статус needs_review.
  Список того, что запускать, берётся из схемы запросом — без модели.

12.5 Зонды (наблюдаемость на связях)
  - Karkas генерирует shared/probe/karkas_probe.hpp — один заголовок:
      KK_PROBE("stream.pump->stream.ring", "fill", n);
    Значения пишутся в неблокирующий кольцевой буфер, фоновый поток
    периодически сбрасывает их в <KARKAS_PROBE_DIR>/<запуск>.jsonl.
    Переменную окружения KARKAS_PROBE_DIR (обычно .karkas/probes)
    выставляет kk_runner; без неё зонды молчат.
  - Полностью выключаются при сборке (KK_PROBES=0): нулевая цена в
    рабочей версии.
  - Индексатор сворачивает сырые данные в сводки (min, max, avg, last)
    и отмечает аномалии (например, буфер опустел).
  - Оркестратор и навигаторы видят только сводки — числа, а не логи:
      probe stream.pump->stream.ring fill min=0 avg=3810 max=8192 anomaly=min0
  - Исполнитель ставит зонды на порты своего листа; это часть шаблона
    листа.


==========================================================================
13. РАБОЧИЕ СЦЕНАРИИ ОТ НАЧАЛА ДО КОНЦА
==========================================================================

13.1 Новый проект
  1. karkas init wavkit, затем karkas design "<идея>".
  2. Архитектор строит верхний уровень: 3–9 блоков, purpose, связи.
  3. ОСТАНОВКА: человек смотрит картинку или вид L0, правит, утверждает.
  4. Архитектор раскрывает каждый составной блок — один вызов на блок; в
     контексте только этот блок, его родитель и соседи. Повторяется,
     пока не выполнены критерии листа (3.9).
  5. Архитектор пишет api/*.hpp для листьев.
  6. ОСТАНОВКА: человек утверждает схему и интерфейсы → api/
     замораживаются.
  7. karkas gen cmake, gen skel, gen mocks, gen probe — без модели.
  8. Тестировщики пишут контрактные тесты листьев.
  9. Исполнители реализуют листья. Интерфейсы заморожены, поэтому все
     листья можно делать ПАРАЛЛЕЛЬНО и в любом порядке: каждому нужны
     только api/ соседей, а не их реализация.
  10. Исполнитель уровня medium пишет корень сборки (entry/compose.cpp)
      по схеме: все связи известны.
  11. Интеграционные тесты групп, итоговая сборка, все блоки passing.

13.2 Новая функция
  Человек: «добавить эффект reverb». Оркестратор по виду L0 выбирает
  dsp. Если существующих блоков хватает — тикет вниз. Если нужен новый
  лист dsp.reverb — запись @change → утверждение → архитектор пишет
  карточку и api/ → тестировщик → исполнитель → регрессия dsp.

13.3 Отладка
  Источник: человек («звук трещит») или упавший тест. Тикет с symptom и
  fact → оркестратор (L0, статусы, зонды) → pick → навигатор(ы) →
  исполнитель листа → @report → результат вверх → регрессия → закрытие.
  Ни один агент выше листа не читает код.

13.4 Перестройка схемы
  Сигналы, которые программа считает сама:
  - у одной пары блоков часто бывает needs_contract_change;
  - тикеты снова и снова проходят через одни и те же два блока;
  - лист перерос критерии листа (строк, портов).
  Тогда Karkas предлагает человеку «переразрезать»: слить или разделить
  блоки. Решение — за человеком, подготовка @change — за архитектором.

13.5 Правка человеком
  Любая правка на картинке или в .ksl → проверка → переиндексация. Если
  затронут контракт, затронутые листья получают статус needs_review.


==========================================================================
14. ГРАФИЧЕСКИЙ ИНТЕРФЕЙС (karkas-gui)
==========================================================================

14.1 Стек
  Dear ImGui (ветка docking) + GLFW 3.4 (Wayland и X11) + OpenGL 3.3 +
  imgui-node-editor (узлы, пины-порты, связи, панорамирование, масштаб) +
  ImGuiColorTextEdit (просмотр кода с подсветкой, только чтение).
  Почему не Qt: ImGui легче, быстрее собирается и мало грузит слабую
  машину, а всё нужное (граф, панели, текст) в нём есть.
  Совместимость: imgui-node-editor может отставать от свежих версий
  ImGui — зафиксировать совместимую пару версий. Запасной вариант —
  imnodes или собственная отрисовка на ImDrawList.

14.2 Раскладка без ИИ
  - Для текущего уровня строится граф, и Graphviz раскладывает его
    алгоритмом dot (rankdir=LR: данные текут слева направо) через
    библиотеки cgraph и gvc. Берутся только координаты узлов, линии
    рисует imgui-node-editor.
  - Размер узла считается заранее по ширине текста.
  - Раскладка кэшируется по хэшу структуры уровня и пересчитывается в
    фоновом потоке.
  - Ручные перемещения человека сохраняются в .karkas/layout/ и важнее
    автоматики.
  - Интерфейс ILayoutEngine позволяет позже заменить Graphviz (на OGDF
    или собственный алгоритм Сугиямы).
  - Если Graphviz сообщает о неизвестном движке раскладки — один раз
    выполнить «sudo dot -c» (регистрация плагинов).

14.3 Масштаб как у карт
  Видны только дети текущего блока. Двойной щелчок по группе — вход
  внутрь (сверху «хлебные крошки» пути). Двойной щелчок по листу —
  панель кода. Режим «все уровни» — вложенные кластеры Graphviz, для
  обзора небольших проектов.

14.4 Панели
  Слева   дерево блоков (оно же дерево папок) со значками статусов
  Центр   схема текущего уровня
  Справа  инспектор блока: карточка KSL (текст и поля), порты, гарантии,
          история, файлы, кнопка «открыть в редакторе»
  Снизу   вкладки: Тикеты (список и trail), Агенты (кто где работает
          сейчас, токены, деньги), Сборка и тесты, Затраты, Дрейф,
          Изменения схемы (ожидают утверждения)

14.5 Цвета
  Блоки: серый — design; синий — api_frozen и tests_ready; жёлтый с
  пульсацией — работает агент; зелёный — passing; красный — failing;
  фиолетовый — drift; оранжевая рамка — needs_review.
  Связи: data — синие, event — оранжевые, call — серые, state —
  красный пунктир, use — скрыты (тонкие, если включены).

14.6 Редактирование схемы на картинке
  Добавить или удалить блок и порт; протянуть связь от out к in (в
  карточку потребителя пишется строка «in … from=…»); разделить или
  слить блок; переименовать (папка переносится, ссылки обновляются).
  Каждое изменение показывается как diff KSL и применяется после
  подтверждения. Предложения агентов (@change) появляются там же с
  кнопками «утвердить» и «отклонить».

14.7 Код
  Просмотр — во встроенной панели. Редактирование — во внешнем
  редакторе; команда задаётся в конфиге, например:
    editor_command = "kitty -e nvim +{line} {file}"

14.8 Мелочи, о которых нельзя забыть
  - Шрифт с кириллицей. В новых версиях ImGui с динамическим атласом
    шрифтов диапазоны глифов не нужны; в старых — GetGlyphRangesCyrillic.
    Учесть масштаб HiDPI.
  - Экономия ресурсов: перерисовка только по событиям
    (glfwWaitEventsTimeout), в простое — почти 0 % процессора.
  - Живые обновления: inotify на .karkas/ и PRAGMA data_version.


==========================================================================
15. MCP-СЕРВЕР И ВНЕШНИЕ АГЕНТЫ
==========================================================================

15.1 Зачем
  Команда karkas mcp отдаёт схему любому агенту с поддержкой MCP (Claude
  Code и др.). Это полезно сразу, ещё до готовности собственных агентов,
  и даёт промежуточный способ B для замеров (раздел 17).

15.2 Реализация
  - Транспорт stdio, JSON-RPC 2.0: одно сообщение — одна строка JSON.
  - stdout — только протокол. Все журналы — в stderr или файл, иначе
    поток протокола ломается.
  - Методы: initialize (согласование protocolVersion, capabilities
    {tools:{}}, serverInfo), notifications/initialized, ping,
    tools/list (name, description, inputSchema), tools/call (name,
    arguments → content [{type:"text", text}], isError).
  - Официального C++ SDK для MCP на момент написания не найдено, есть
    общественные (cxxmcp, mcpp, gopher-mcp и др.). Решение для v1 —
    своя минимальная реализация на nlohmann/json (примерно 300–500
    строк): протокол для инструментов по stdio небольшой, а лишняя
    зависимость обходится дороже. Актуальную версию спецификации
    сверить на modelcontextprotocol.io.
  - Ответы инструментов — компактный KSL-текст, а не громоздкий JSON:
    так дешевле по токенам.

15.3 Инструменты MCP
  kk_overview · kk_view(block, level) · kk_children · kk_neighbors ·
  kk_dependents · kk_path · kk_search · kk_history · kk_status ·
  kk_probes · kk_drift · kk_ticket_view(id) · kk_ticket_append(id, line)
  · kk_run_tests(block)
  У каждого — inputSchema (JSON Schema) и короткое описание на
  английском. Внимание: в Claude API поле называется input_schema, в
  MCP — inputSchema.

15.4 Подключение к Claude Code
  Например: claude mcp add karkas -- karkas mcp --project <путь>
  или файл .mcp.json в корне целевого проекта. Точный синтаксис сверить
  с документацией Claude Code (claude mcp --help) на момент
  подключения.

15.5 Проверка
  MCP Inspector (официальный инструмент проверки MCP-серверов) +
  собственные «золотые» тесты: записанные пары запрос/ответ JSON-RPC.

==========================================================================
16. УЧЁТ ТОКЕНОВ И ЗАТРАТ
==========================================================================

16.1 Что записывается на каждый вызов модели
  время, тикет, роль, блок, провайдер, модель, уровень, номер попытки,
  input_tokens, output_tokens, cache_creation_input_tokens,
  cache_read_input_tokens, длительность, число шагов, исход.
  Источник чисел — поле usage ответа API (оно точное). Локальная оценка
  токенов нужна только для бюджетов до отправки запроса.

16.2 Деньги
  cost = ( input       × цена_входа
         + cache_write × цена_входа × 1,25   (кэш на 5 минут; на 1 час ×2)
         + cache_read  × цена_входа × 0,1
         + output      × цена_выхода ) / 1 000 000
  Цены — таблица [prices] в конфиге (USD за 1 млн токенов); заполнить по
  официальной странице цен. Коэффициенты кэша — там же. Если цена
  облачной модели не задана, karkas cost и bench выдают ошибку, а не
  молча считают ноль.
  Локальные модели: деньги 0, но токены и время считаются.

16.3 Отчёты
  karkas cost [--by block|role|model|ticket] [--since <дата>]
  В GUI — вкладка «Затраты»: итоги, по блокам, доля чтения из кэша,
  стоимость каждого тикета.

16.4 Запись и воспроизведение (record/replay)
  kk_llm умеет записывать пары «запрос → ответ» в файлы и
  воспроизводить их. Это нужно для тестов логики агентов без денег и
  без сети и для отладки. В CI — только воспроизведение.


==========================================================================
17. МЕТОДИКА ЗАМЕРОВ
==========================================================================

17.1 Цель и гипотезы
  Проверить, даёт ли Karkas выигрыш по токенам, деньгам и времени при
  сопоставимом качестве, и где именно этот выигрыш возникает.
  H1 На создании небольшого проекта с нуля Karkas не выигрывает или
     проигрывает (накладные расходы на схему).
  H2 На доработках и отладке Karkas тратит в разы меньше токенов.
  H3 Выигрыш растёт с размером проекта.
  H4 Качество (доля пройденных скрытых приёмочных тестов) не хуже.

17.2 Способы
  A  Обычный агент: Claude Code в неинтерактивном режиме
     (claude -p … --output-format json), без Karkas.
  B  Claude Code + MCP-сервер Karkas: граф доступен, но без нашей
     иерархии агентов и маршрутизации. Отделяет эффект «навигации по
     схеме» от эффекта «раздачи работы дешёвым моделям».
  C  Полный Karkas: архитектор, оркестратор, навигаторы, исполнители,
     тестировщики, маршрутизация.
  Для A и B — два варианта модели (сильная и средняя), чтобы честно
  сравнить с маршрутизацией C.

17.3 Тестовый проект: wavkit (предложение)
  Консольный аудиоконвейер: чтение WAV (PCM16, float32), эффекты (gain,
  low-pass, echo), микширование нескольких дорожек, запись WAV. Поток
  чтения передаёт кадры обработке через кольцевой буфер. 8–12 листьев.
  Почему он: не нужно звуковое устройство, поэтому тесты
  детерминированы (файл на входе → файл на выходе, сравнение с
  эталоном с допуском); есть потоки и буфер, значит, можно
  воспроизвести класс багов «звук трещит».
  ТЗ ДОЛЖНО точно фиксировать интерфейс командной строки и форматы:
  тогда скрытые приёмочные тесты работают одинаково для любой
  внутренней структуры. Альтернатива — любой проект того же масштаба,
  который тестируется без участия человека.

17.4 Сценарии
  S1 Создание с нуля по одному ТЗ (bench/wavkit/spec.md).
  S2 Пять доработок подряд: reverb, панорама, нормализация, пакетная
     обработка папки, отчёт о ходе работы.
  S3 Отладка: пять заранее внесённых багов в ОДНУ И ТУ ЖЕ эталонную
     кодовую базу для всех способов (для A файлы .ksl и папка .karkas
     удаляются). Баги: ошибка на единицу на границе кольцевого буфера
     (треск), двойное применение gain, нет защиты от клиппинга при
     микшировании, переполнение обратной связи в echo, неверный порядок
     байт при записи. Каждый баг подаётся как симптом словами
     пользователя + один факт (упавший тест или наблюдение).

17.5 Что измеряется
  - токены: вход, выход, запись и чтение кэша — по моделям;
  - деньги (USD); время по часам; число вызовов модели;
  - число вмешательств человека;
  - доля пройденных СКРЫТЫХ приёмочных тестов;
  - для багов: исправлен ли баг и не сломано ли остальное;
  - дополнительно: предупреждения компилятора, замечания clang-tidy,
    объём кода.
  Для A и B: брать total_cost_usd и разбивку по моделям (modelUsage) из
  JSON-результата Claude Code. Claude Code может вызывать
  вспомогательные модели, и поле usage показывает не всё.

17.6 Правила честности
  - Одно ТЗ, одни и те же модели, одинаковые лимиты шагов и бюджета.
  - Скрытые приёмочные тесты пишутся заранее, хранятся ВНЕ репозитория
    и запускаются только харнессом после прогона. Ни один способ их не
    видит.
  - Минимум 3, лучше 5 прогонов на способ и сценарий. В отчёте —
    медиана и разброс (минимум–максимум).
  - Затраты на создание самой программы Karkas в замер не входят;
    затраты на построение схемы тестового проекта входят обязательно.
  - Каждый прогон — в свежей копии репозитория. Кэш промптов не должен
    переходить между прогонами (пауза дольше срока жизни кэша или
    уникальная метка в начале промпта).
  - Вмешательства человека записываются. Утверждение схемы в способе C
    — тоже вмешательство.
  - Для A — минимальный стартовый контекст Claude Code: без
    посторонних плагинов, хуков и инструкций (в текущих версиях есть
    флаг --bare). Для B — то же, но MCP-сервер karkas подключается
    явно (например, через --mcp-config). По документации --bare
    пропускает загрузку MCP-серверов, поэтому для B проверить, как эти
    флаги сочетаются. Точные флаги (--max-turns, --max-budget-usd,
    --model и др.) сверить с claude --help на момент замеров.
  - Все способы работают через ключ API, а не через подписку: так
    деньги сравнимы между собой.

17.7 Харнесс
  karkas bench run --scenario s1|s2|s3 --method A|B|C --model <имя> --reps 5
  - A/B: запускает claude -p в копии репозитория с --output-format json,
    лимитами шагов и бюджета; сохраняет JSON целиком.
  - C: запускает конвейер Karkas, данные берёт из таблицы runs.
  - После каждого прогона: сборка + скрытые приёмочные тесты.
  - Результаты: bench/results/<дата>/<сценарий>-<способ>-<n>.json.
  karkas bench report → CSV + сводная таблица (текст и HTML) с медианами.

17.8 Критерий вывода (предложение, утверждает человек)
  Karkas полезен, если на S2+S3 медианные деньги ниже минимум на 40 % при
  доле скрытых тестов не ниже, чем у лучшего варианта A. Если выигрыша
  нет, отчёт ДОЛЖЕН показать, на каком этапе съедаются токены (по данным
  runs), — это тоже ценный результат.

  репозитории — это первая проверка на реальном проекте.

19.2 Корневой CMakeLists.txt — основные решения
  cmake_minimum_required(VERSION 3.29)
  project(karkas VERSION 0.1.0 LANGUAGES C CXX)
  CMAKE_CXX_STANDARD 23, CMAKE_CXX_STANDARD_REQUIRED ON,
  CMAKE_CXX_EXTENSIONS OFF, CMAKE_EXPORT_COMPILE_COMMANDS ON (для clangd)
  option(KARKAS_GUI         "Build GUI"             ON)
  option(KARKAS_TESTS       "Build tests"           ON)
  option(KARKAS_SANITIZERS  "ASan + UBSan"          OFF)
  option(KARKAS_SYSTEM_DEPS "Prefer system packages" ON)
  Каждая библиотека: add_library(kk_<name>) + псевдоним karkas::<name>,
  target_include_directories(PUBLIC include), target_compile_features
  (cxx_std_23), предупреждения — через kk_set_warnings.
  В корне — символическая ссылка compile_commands.json на файл в
  папке сборки dev (для clangd в редакторе).

19.3 Пресеты (CMakePresets.json)
  dev       Ninja, Debug, ccache, mold, тесты включены
  release   Ninja, Release, LTO (IPO)
  asan      Ninja, Debug, KARKAS_SANITIZERS=ON
  headless  Ninja, Release, KARKAS_GUI=OFF (сервер, CI)
  Команды:
    cmake --preset dev
    cmake --build --preset dev
    ctest --preset dev

19.4 Сборка на слабой машине
  - ccache (CMAKE_CXX_COMPILER_LAUNCHER) и mold (CMAKE_LINKER_TYPE=MOLD).
  - Пулы заданий Ninja: компиляция — по числу ядер, линковка — одна за
    раз (JOB_POOLS link=1), чтобы не упираться в память.
  - Предкомпилированные заголовки (target_precompile_headers) для
    тяжёлых: nlohmann/json, spdlog, imgui.
  - В заголовках — nlohmann/json_fwd.hpp; полный json.hpp — только в .cpp.
  - Сторонний код (ImGui, node-editor, tree-sitter) — отдельные
    статические цели, собираются один раз.
  - CMake 4.x не собирает сторонние проекты с
    cmake_minimum_required < 3.5. Для них — своя цель из исходников
    или CMAKE_POLICY_VERSION_MINIMUM=3.5.

19.5 Качество кода
  - Предупреждения: -Wall -Wextra -Wpedantic -Wshadow -Wconversion
    -Wnon-virtual-dtor -Wold-style-cast; -Werror — только в CI.
  - .clang-format (основа LLVM, ширина 100), .clang-tidy (bugprone-*,
    performance-*, modernize-*, readability-identifier-naming).
  - Имена: пространства имён kk::<модуль>; типы PascalCase; функции и
    переменные snake_case; константы kName.
  - Тесты: doctest + CTest (doctest_discover_tests); у каждой
    библиотеки свой тестовый исполняемый файл; метка ctest = имя
    библиотеки.
  - Покрытие (по желанию, gcovr): цель ≥ 70 % для core, index, code.

ПРИЛОЖЕНИЕ A. Пример схемы: wavkit
--------------------------------------------------------------------------

project.ksl
  @project wavkit
  idea    CLI audio pipeline: read WAV files, apply effects, mix tracks, write WAV
  lang    cpp
  build   cmake-ninja
  std     c++20
  test    doctest
  rule    blocks talk only through api/ headers
  rule    no exceptions across block boundaries, use Result<T>

Дерево блоков
  app            entry   CLI args, composition root, run loop
  io             group   WAV file input/output
    io.reader    leaf    parse WAV (PCM16, float32) into normalized float frames
    io.writer    leaf    write frames to a WAV file
  stream         group   move frames from reader thread to processing
    stream.pump  leaf    reader thread that moves frames from io.reader into stream.ring
    stream.ring  leaf    lock-free single-producer single-consumer ring of audio frames
  dsp            group   effect chain applied to frames
    dsp.chain    leaf    run configured effects over frames in a fixed order
    dsp.gain     leaf    multiply samples by gain
    dsp.lowpass  leaf    one-pole low-pass filter
    dsp.echo     leaf    feedback delay line
  mix            leaf    mix N tracks with per-track gain, clip-safe
  shared.types   shared  Frame, AudioFormat, Result<T>
  shared.log     shared  logging
  shared.probe   shared  Karkas probes (generated)

blocks/io/reader/block.ksl
  @block io.reader
  purpose parse WAV (PCM16, float32) into normalized float frames
  kind    leaf
  thread  reader
  est     S
  out     frames Frame[]
  fn      open(path) -> Result<AudioFormat>
  use     shared.types
  inv     rejects unsupported formats with an error, never crashes
  inv     PCM16 samples map into [-1, 1]

blocks/stream/pump/block.ksl
  @block stream.pump
  purpose reader thread that moves frames from io.reader into stream.ring
  kind    leaf
  thread  reader
  est     S
  in      src    Frame[]  from=io.reader:frames link=data via=direct
  out     frames Frame[]
  fn      start() -> void
  fn      stop() -> void
  use     shared.types
  use     shared.probe
  inv     stops cleanly on end of file and on stop()

blocks/stream/ring/block.ksl
  (см. раздел 4.4)

blocks/dsp/chain/block.ksl
  @block dsp.chain
  purpose run configured effects over frames in a fixed order
  kind    leaf
  thread  main
  est     S
  in      in   Frame[]  from=stream.ring:pop link=data sync=lock_free
  out     out  Frame[]
  call    dsp.gain:process
  call    dsp.lowpass:process
  call    dsp.echo:process
  use     shared.types
  inv     output length equals input length
  inv     an empty chain passes frames through unchanged

Вид L0 и вид L1 для этого проекта — в разделе 4.7.

templates/prompts/architect.txt
  You are the ARCHITECT. Decompose {{target}} into 2-9 child blocks.
  For each child output a KSL @block record: id, kind (group|leaf),
  one-sentence purpose in English, thread, est (S|M|L), ports, links,
  invariants. A child is a leaf only if: single responsibility,
  <= ~400 lines, <= 6 ports, one thread, testable through its ports
  with mocks. Prefer data links over shared state. Declare via= for
  every thread crossing. Output only KSL records, no prose.
  For leaves also write api/ headers in C++: abstract interfaces and
  plain data types, no implementation, dependencies via constructor.

templates/prompts/orchestrator.txt
  You are the ORCHESTRATOR of a project represented as a hierarchical
  schema of blocks. You never see source code. You get: the project idea,
  the L0 view with statuses, and a ticket.
  Decide which top-level block most likely contains the cause (bug) or
  must change (feature). Use schema tools only; prefer the cheapest query
  that answers your question. Never rewrite symptom or fact lines. Add at
  most 2 new facts, only if observed via tools.
  If new blocks, ports or links are needed, call propose_change with a
  KSL diff. Otherwise call dispatch with one trail entry:
  suspect, ruled_out, difficulty (S|M|L), why (<= 20 words).

templates/prompts/navigator.txt
  You are the NAVIGATOR of group block {{block}}. You never see source
  code. You get: the parent purpose, the L1 view of your block, probe
  summaries on internal links, and the ticket path view.
  Pick the child most likely responsible and call dispatch with one
  trail entry. If the problem is clearly outside your block, call
  report(status=not_here) with evidence. Use ask(child, question) only
  when one short answer would change your pick.

templates/prompts/worker.txt
  You are the WORKER for leaf block {{block}}. You work only inside this
  block's folder. You get: the L2 view (card, ports, invariants), the
  block's api/ headers (frozen contract), api/ headers of linked
  neighbors, your impl/ and tests/unit/ files, the ticket path view,
  and the last build/test summary.
  Rules: do not change api/; if the fix needs a contract change, stop
  and report status=needs_contract_change with a minimal proposal. Keep
  changes minimal. When fixing a bug, first add a unit test that
  reproduces it. Run build() and test() before reporting. If the cause
  is outside this block, report status=not_here with evidence.
  Finish with report(status, cause, fix, files, tests, api).

templates/prompts/tester.txt
  You are the TESTER for leaf block {{block}}. You never read impl/.
  Write contract tests in tests/contract/ (doctest) that check every
  invariant and every port of the card through the api/ headers, using
  mocks/ for neighbors. Name each test case after its invariant. For
  buffers and numeric code prefer loops over many inputs to single
  examples. Run build() and test(). Report covered invariants and
  results. Failing tests against an unimplemented block are expected.

ПРИЛОЖЕНИЕ D. Вид пути тикета на каждом уровне
--------------------------------------------------------------------------

Оркестратор (уровень 0) получает:
  @ticket T-0042 view=path at=root
  kind    bug
  symptom crackle in output after ~10 s of playback, worse with echo enabled
  fact    contract stream.ring/no_drop FAIL: dropped=37 of 480000 frames
  fact    probe stream.pump->stream.ring fill_min=0 at t=9.8s

Навигатор stream (уровень 1) получает то же + запись уровня 0:
  --- trail
  L0 orchestrator at=root pick=stream difficulty=M why="frames dropped before dsp; ring runs empty"
  (suspect=dsp из записи L0 не передаётся: это другая ветка)

Исполнитель stream.ring (уровень 2) получает то же + запись уровня 1:
  L1 navigator at=stream ruled_out=stream.pump pick=stream.ring why="pump rate ok 48k/s; drops at wraparound"

Итого на уровне 2 — около 150–200 токенов вместо пересказа всего
проекта.

ПРИЛОЖЕНИЕ F. CLAUDE.md для репозитория Karkas
--------------------------------------------------------------------------

  # Karkas — instructions for the coding agent

  Spec: docs/SPEC.txt. Read sections 0 and 20 first, then the section
  of the current stage. Current stage and status: docs/progress.md.

  Build:  cmake --preset dev && cmake --build --preset dev
  Test:   ctest --preset dev
  One lib: ctest --preset dev -L core

  Rules:
  - Work stage by stage. Small steps; after each step the build and
    tests are green and the change is committed.
  - C++23, namespace kk::<module>, no exceptions across module
    boundaries (std::expected).
  - No new dependencies without docs/adr/NNNN-*.md.
  - Deterministic first: never call an LLM where an algorithm works.
  - Tests for agent logic use recorded LLM responses (replay); no
    network in tests.
  - In MCP mode never write to stdout except protocol messages.
  - Keep headers light: nlohmann/json_fwd.hpp in headers.
  - At the end of each stage update docs/progress.md; record any
    deviation from the spec in docs/adr/.

ПРИЛОЖЕНИЕ G. Справка по командам CLI

  karkas init <dir>                       создать целевой проект
  karkas design "<идея>"                  архитектор: верхний уровень (ждёт утверждения)
  karkas expand <block> [--all]           раскрыть блок или все блоки
  karkas approve <C-NNNN | L0 | api>      утвердить изменение, уровень или интерфейсы
  karkas check                            проверка KSL и дрейфа
  karkas index [--watch]                  индексация
  karkas view [<block>] [--level 0|1|2]   вид для модели
  karkas query <запрос> <аргументы>       neighbors, dependents, path, writers …
  karkas gen cmake|mocks|probe|skel       генерация
  karkas implement <block | all>          тестировщики и исполнители листьев
  karkas test [<block>]                   сборка и тесты (без модели)
  karkas task "<описание>"                задача через оркестратор
  karkas debug "<симптом>" [--fact "…"]   отладка спуском по схеме
  karkas ticket list | show <id> [--path] тикеты
  karkas cost [--by …]                    затраты
  karkas mcp [--project <dir>]            MCP-сервер (stdio)
  karkas bench run | report …             замеры
  karkas gui                              графический интерфейс
